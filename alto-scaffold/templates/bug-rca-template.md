# Bug RCA Document Template

Copy this template to `docs/bugs/YYYYMMDD_<bug-id>_<slug>.md` for any **S0
or S1 bug**. (S2/S3 bugs keep their RCA inline on the ticket; this
separate document is overkill for cosmetic defects.)

Generated by `/rca <bug-id>` or hand-authored. Update the document as you
move through investigation → fix → verification — the final state should
read as a complete post-mortem that someone with no prior context can
follow end-to-end.

---

```markdown
# Bug RCA: <one-line title> (<bug-id>)

**Date filed:** YYYY-MM-DD
**Bug ticket:** <bug-id> (`bd show <bug-id>`)
**Severity:** S0 / S1
**Status:** Investigating | Root cause identified | Fixed | Verified | Closed
**Author(s):** <names>
**Detection source:** User report | CI on main | CI on branch | Internal dogfood | Code review | Other

> **Blameless principle:** This document describes how the system permitted
> the bug, not which person typed which characters. If you find yourself
> writing "X forgot" or "Y didn't notice", ask one more "why" and keep
> going.

## Summary

One paragraph (≤ 4 sentences) covering: what broke, who felt it, how long,
and what the root cause turned out to be. Treat this as the abstract — a
reader who only reads this paragraph should understand the whole incident.

## Impact

- **Who was affected?** (users / agents / CI / dogfood)
- **What did they observe?** (one or two concrete behaviours)
- **For how long?** (introduced at commit X, observed at time Y, fixed at
  commit Z — total exposure window)
- **Was data lost or corrupted?** If yes, what + how recovered.
- **Are there known stragglers?** (e.g. ticket fixtures still in the DB, log
  entries that need rewriting, downstream caches to bust)

## Five Whys

Whys 1–2 describe the incident. **Whys 3–5 describe the system that
allowed it** — missing test, missing type, missing rule, mismatched
ownership, mis-prioritised guard. If you stop at why 2, your action item
is a one-off patch. If you reach why 5, your action item is structural.

## Detection gap

Why didn't existing tests, lint rules, CI gates, or dogfood catch this
earlier? **Every bug has a detection gap by definition** — the gap is the
distance between when the bug was introduced and when it was noticed.

## Fix

| Field | Detail |
|-------|--------|
| **Approach** | One paragraph: what the fix does and why this approach |
| **Files changed** | Bulleted list with `path/to/file.go:lines` or just paths |
| **Regression test** | `Test<Name>` in `path/to/test_file` — what it asserts |
| **Fix commit** | `<hash>` (link if external review tool used) |
| **Lines of code** | Net diff stat (`+X / -Y`) |

If the fix was non-trivial, explain alternatives considered and why they
were rejected.

## Verification

### Before fix — REPRODUCE

```
commit: <hash>  (the commit just before the fix landed)
$ <command that triggers the bug>

<verbatim failure output>
```

### After fix — RESOLVED

```
commit: <hash>  (the fix commit)
$ <same command>

<verbatim success output>
```

### Regression guard — FUTURE-PROOF

The test added in the fix commit (`Test<Name>` in `<file>`) will fail if
the same bug is reintroduced. **Removing this test in a future PR requires
written justification.**

If the fix touches a code path with no existing test scaffolding, note
what new coverage shape was added (e.g. "first table-driven test in
this package; future bugs here can extend it").

## Action items

Concrete follow-ups from the Five Whys' system-layer answers. Each item
gets an owner and either becomes a separate beads ticket or is checked off
inline. **Action items without an owner or a ticket do not get done.**

- [ ] <Item> — owner: \_\_\_ — ticket: `<bd-id>` (or "this doc only")
- [ ] ...

Common action-item shapes:

- Add a static check / lint rule that would have caught this class
- Tighten a type so the invariant the bug broke is unrepresentable
- Add an integration test for the path the unit tests missed
- Document the invariant in the relevant ADR or DDD glossary
- Schedule a related cleanup ticket for the contributing factors

- [ ] Document moved from `Status: Investigating` to `Status: Closed`
```
